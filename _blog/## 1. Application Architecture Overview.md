## ## 1. Application Architecture Overview

The **Docling Factory** is designed as a multimodal document processing pipeline. It transforms unstructured documents (PDFs, Docx, etc.) into structured formats and provides an interactive chat interface to query those documents using a local or remote LLM.  



### ### Key Components

- **Web Interface:** Built with **Gradio**, providing a multi-tabbed UI for uploading, parsing, and chatting.  

  

  

- **Parsing Engine (`DoclingParser`):** Leverages the `docling` library for layout-aware document conversion.  

  

  

- **RAG Engine (`RAGEngine`):** Orchestrates semantic search using **OpenSearch** as a vector database and **Ollama** or **LiteLLM** for embeddings and text generation.  

  

  

- **Observability:** Integrated with **OpenLLMetry** and a custom **MetricsCollector** to track latency, token usage, and system health.

## ## 2. Core Modules and Functionality

### ### A. Document Parsing (`docling_parser.py`)

The `DoclingParser` class is the heart of the ingestion pipeline. It handles various file types and output formats.

- **Multimodal Support:** It can extract figures (saved as PNGs) and captions from PDF documents using `PictureItem` detection.  

  

  

- **OCR Integration:** Supports multiple OCR engines including **RapidOCR** (recommended), **EasyOCR**, **Tesseract**, and **macOS Vision**.  

  

  

- **Specialized Parsers:** Beyond standard documents, it includes logic for parsing **CSV** files via Pandas and **XBRL** financial documents using `lxml`.  

  

  

- **Code Correlation:** In `app_enhanced.py`, the `parse_single_file` function calls `parser.parse_document`, passing user-selected options like `ocr_engine` and `export_figures`.  

  +1

  

### ### B. RAG & Vector Storage (`rag_engine.py`)

The RAG system enables "Chat with Documents" by indexing parsed text into a vector space.

- **Vector Database:** Uses **OpenSearch** with k-NN (k-Nearest Neighbors) search enabled. It uses the `lucene` engine and `cosinesimil` space type for vector comparisons.  

  

  

- **Hybrid Backend:**

  - **Ollama:** For local execution of models like `llama3.2` and `granite-embedding`.  

    

    

  - **LiteLLM:** Acts as an AI Gateway to connect to remote providers (OpenAI, Anthropic) or proxied local models.  

    

    

- **Chunking:** Employs `RecursiveCharacterTextSplitter` with a chunk size of 500 characters and 100-character overlap to ensure context is preserved without exceeding model limits.  

  

  

### ### C. Deployment & Infrastructure (`docker-compose.yml`)

The application is containerized to manage its various microservices:

| Service             | Purpose                                                      |
| ------------------- | ------------------------------------------------------------ |
| **opensearch**      | Vector database for storing document embeddings.             |
| **litellm**         | Unified API gateway for LLM access.                          |
| **litellm-db**      | PostgreSQL backend for LiteLLM's internal data.              |
| **docling-factory** | The main Python application (available in CPU and GPU versions).  +2 |

## ## 3. How the Implemented Code Works

### ### Document Processing Flow

1. **Upload:** User uploads a file through the Gradio `file_input`.  

   

   

2. **Conversion:** `DoclingParser` converts the file to Markdown. If it's a PDF with no selectable text, the selected OCR engine (e.g., `rapidocr`) is triggered.  

   

   

3. **Indexing:** If "Index for RAG" is checked, the `RAGEngine.index_document` method is called. It splits the Markdown into chunks, generates embeddings via `OllamaEmbeddings` or `LiteLLMEmbeddings`, and performs a bulk upload to the OpenSearch index.  

   +1

   

### ### Retrieval & Chat Flow

1. **Search:** When a user asks a question, the `RAGEngine.search` method converts the query into a vector and finds the top *k* most similar chunks in OpenSearch.  

   

   

2. **Augmentation:** The retrieved text is stuffed into a prompt template: *"Context information: {context} ... Question: {prompt}"*.  

   

   

3. **Generation:** The LLM generates an answer based strictly on the provided context.  

   

   

### ### Observability Dashboard

The `MetricsCollector` uses OpenTelemetry to intercept spans from LLM calls. The `standalone_dashboard.py` script can then generate a visual representation of this data using Plotly, showing error rates, token costs, and P95/P99 latency percentiles.

## ## 4. Quick Start Summary

To run the system as described in the documentation:

1. Start the infrastructure: `docker-compose up -d opensearch litellm`.  

   

   

2. Launch the application: Run `python app_enhanced.py`.  

   

   

3. In the UI, initialize the RAG engine and begin uploading documents for parsing and indexing.
